Portal Safe Browsing Monitor

定时用浏览器打开 Google Safe Browsing Transparency Report， 检查配置域名是否被标记为危险站点，只在安全状态真正变化时通过 Microsoft Teams Webhook 通知。

做什么 怎么检查 状态与通知 仓库结构 怎么跑 K8s 部署 CI / CD

这个仓库解决什么问题

Google 会把恶意、钓鱼、被入侵的站点标成 unsafe。 本项目不调官方 API，而是用 Playwright 打开公开页面 transparencyreport.google.com/safe-browsing/search， 读取页面上的英文结论，再和上次结果对比。

适合盯一组业务域名（例如 portal），发现「从未 unsafe → 变成 unsafe」或「unsafe → 又变回 safe」时立刻告警， 状态没变就不刷屏。

一次运行做了什么

读 domains.txt（跳过空行和 # 注释，去重） ↓ 读 status.json（每个域名上次有效的 SAFE / UNSAFE） ↓ 启动浏览器：本机用 Google Chrome；Docker / K8s 用 Playwright Chromium（无头） ↓ 对每个域名打开 Transparency Report，解析页面文案 ↓ 最多重试 3 次（UNKNOWN / 异常会重试） ↓ 决定要不要写新状态、要不要发 Webhook ↓ 原子写入 status.json（先写 .tmp 再 replace）

核心逻辑都在 app/monitor.py。依赖只有 playwright==1.62.0。 Docker 镜像基于 mcr.microsoft.com/playwright/python:v1.62.0-noble， 容器里已经带 Chromium。

状态机：什么会通知，什么不会

解析页面得到五种结果：

状态含义怎么判定
UNSAFE Google 明确说站点不安全 页面含 this site is unsafe 等
SAFE Google 明确说没发现不安全内容 no unsafe content found / this site is safe 等
NO_DATA Google 暂时没有该站数据 no available data
UNKNOWN 无法给出全站简单结论（大站常见），或页面没解析出来 对应英文说明；解析失败也会落到这里，并写 debug 文件
CHECK_ERROR 检测过程异常（导航失败等） 重试耗尽后仍失败

会发 Teams 的情况

  • 第一次检查就是 UNSAFE
  • 有效状态在 SAFE ↔ UNSAFE 之间切换（告警或恢复）

故意不通知、也不覆盖旧状态

  • SAFE → SAFE、UNSAFE → UNSAFE：无变化
  • 第一次是 SAFE：只落盘，不发「都正常」的消息
  • UNKNOWN / NO_DATA / CHECK_ERROR：不当作安全结论变化；若已有上次 SAFE/UNSAFE，会保留旧值，避免一次页面抽风把状态冲掉、或反复告警
status.json 只存「每个域名最后一次有效的 SAFE 或 UNSAFE」，不存历史。 文件不会随 CronJob 次数变大。Webhook 未配置时仍会跑检查并写状态，只是跳过 POST。

仓库里各文件干什么

路径作用
app/monitor.py全部监控、解析、状态、Webhook 逻辑
domains.txt本地默认域名列表（K8s 会被 ConfigMap 覆盖挂载）
DockerfilePlaywright 镜像；状态写到 /data/status.json
k8s/configmap.yaml集群里实际监控哪些域名
k8s/pvc.yaml + storageclass.yamlEBS gp3，跨 Job 保留状态
k8s/job.yaml一次性试跑
k8s/cronjob.yaml定时跑（当前 schedule 为每 10 分钟，Forbid 禁止重叠）
.github/workflows/docker-publish.ymlmain / tag 构建并推 Docker Hub jevinwanglb/portal-monitor
.github/workflows/cd.yml手动指定 tag，在 EKS 上跑测试 Job

不要提交 status.json、debug 截图、Webhook URL。 Teams URL 只放环境变量或 K8s Secret portal-monitor-alert 的 webhook-url。

三种运行方式

本机

venv 装依赖，用系统 Chrome（有界面）。

export ALERT_WEBHOOK_URL=…
python app/monitor.py

公司 Zero Trust 导致 Webhook 证书失败时，可临时 WEBHOOK_VERIFY_TLS=false（不要当生产默认）。

Docker

无头 Chromium，状态挂到宿主机目录。

-v $PWD/docker-state:/data
PLAYWRIGHT_HEADLESS=true

镜像里默认 STATE_FILE=/data/status.json。

重要环境变量：DOMAINS_FILE、STATE_FILE、PLAYWRIGHT_HEADLESS、 IGNORE_HTTPS_ERRORS（无头模式默认真，本机默认真否）、 ALERT_WEBHOOK_URL、WEBHOOK_VERIFY_TLS、以及超时/重试相关项。

Kubernetes 怎么拼在一起

Namespace: portal-monitor ↓ ConfigMap portal-monitor-config → 挂到 /app/domains.txt（改域名只需 apply ConfigMap，不用重建镜像） ↓ Secret portal-monitor-alert → ALERT_WEBHOOK_URL ↓ PVC portal-monitor-state (gp3) → /data/status.json ↓ 先 Job 验证，再 CronJob 周期执行

StorageClass 是 WaitForFirstConsumer：PVC 一开始可能 Pending，等第一个 Job Pod 调度后 EBS 才 Bound。 删 Job 不要删 PVC，否则下次会当成「第一次检查」再次告警。

CronJob 镜像当前为 jevinwanglb/portal-monitor:v1.0.0； 测试 Job YAML 里仍可能写着旧仓库名 jevinwanglb/repo:portal-monitor-v1， CD workflow 会用 sed 换成指定 tag 再 apply。

构建与发布

  • docker-publish：push 到 main（且改了 app / Dockerfile / requirements 等）或打 v* tag， 构建 linux/amd64 推 Docker Hub。commit 得到 sha-… tag，Git tag 得到版本 tag。
  • cd：workflow_dispatch，输入 image tag，在 runner arc-runner-set-portal 上 删掉旧的 portal-monitor-test Job，apply 新 Job，等到 complete 并打日志。目前不自动改 CronJob。
