portal-monitor

Portal Safe Browsing Monitor

用 Playwright 打开 Google Safe Browsing Transparency Report，检查配置的域名或 URL。 只有有效安全状态变化时，才通过 Teams Webhook 通知。Production 跑在 EKS CronJob 上，每 10 分钟一次。

Overview 1. Local 2. Docker 3. Kubernetes 4. CI / CD 排障

Overview

这个仓库解决什么问题

不调用 Safe Browsing Lookup API，而是用浏览器打开公开页面 transparencyreport.google.com/safe-browsing/search， 读取页面英文结论，再和 status.json 里上次结果对比。

  1. 1

    打开 Transparency Report

    对本机 Chrome 或容器 Chromium，串行检查每个域名 / URL。

  2. 2

    解析成五种状态

    SAFE / UNSAFE / UNKNOWN / NO_DATA / CHECK_ERROR

  3. 3

    和 status.json 比较

    只有 SAFE ↔ UNSAFE 变化（含首次 UNSAFE）才发 Webhook。

  4. 4

    通知 Microsoft Teams

    经 Power Automate Workflow 触发器投递到频道。

适合盯一组业务域名或具体 path。状态没变不刷屏； UNKNOWN / NO_DATA / CHECK_ERROR 不会覆盖已经落盘的有效 SAFE / UNSAFE。

一次运行做了什么

入口是 app/monitor.py，依赖只有 playwright==1.62.0。

  1. 读域名列表（本机 domains.txt；K8s 挂 ConfigMap 到 /app/domains.txt）。跳过空行和 #，去重并保序。
  2. 读状态文件（本机 status.json；容器 /data/status.json）。不存在则视为空。
  3. 启动浏览器：本机有界面 Chrome；Docker / K8s 用无头 Chromium。
  4. 逐个打开 Transparency Report，等待已知结论文案（约 20s），解析页面文本。
  5. UNKNOWN 或异常最多重试 3 次。
  6. 决定是否覆盖状态、是否加入通知队列。
  7. 先写 status.json.tmp 再原子替换，避免写一半损坏。
  8. 对每个 status_changed 事件 POST 到 ALERT_WEBHOOK_URL。

检查是串行的。域名多、页面慢、或频繁 UNKNOWN 重试时，单次 Job 可能跑几分钟。

CronJob 使用 concurrencyPolicy: Forbid：上一轮没结束，下一轮自动触发会被跳过。

Status

状态 含义 页面特征（英文，忽略大小写）
UNSAFE 整站或部分页面有风险 this site is unsafe site is unsafe some pages on this site are unsafe pages on this site are unsafe contains harmful content
SAFE 明确没有问题 no unsafe content found no issues found this site is safe
NO_DATA Google 暂无数据 no available data
UNKNOWN 无法给简单结论，或文案对不上 it's hard to provide a simple safety status （大站常见）；解析失败也会落到这里
CHECK_ERROR 访问或检测异常，重试耗尽 运行异常，不是 Google 给出的安全结论

部分 URL（例如官方测试站 testsafebrowsing.appspot.com/apiv4/.../URL/） 页面写的是 Some pages on this site are unsafe， 不是 This site is unsafe。

等待和解析必须同时认这两种说法，否则会超时 → UNKNOWN → 不告警。 这类测试 URL 本是给 Safe Browsing API 用的，但 Transparency Report 网页也会返回「部分页面不安全」。

Alert Logic

会通知

  • 第一次有效检查就是 UNSAFE
  • 已有状态在 SAFE ↔ UNSAFE 之间切换

Payload：event: status_changed，含 domain / previous / current / time。

不通知

  • SAFE → SAFE、UNSAFE → UNSAFE
  • 第一次是 SAFE（只落盘）
  • UNKNOWN / NO_DATA / CHECK_ERROR
  • 未配置 Webhook（仍检查、仍写状态）

遇到 UNKNOWN / NO_DATA / CHECK_ERROR 时，若该域名已有上次 SAFE / UNSAFE，会保留旧值， 避免一次页面抽风冲掉状态。首次一直 UNKNOWN 时，status.json 里可以没有这条 key。

status.json 只存每个条目最后一次有效 SAFE / UNSAFE，不存历史。

1. Local

venv 装依赖，用本机 Google Chrome。

export ALERT_WEBHOOK_URL='…'
python app/monitor.py

Zero Trust 证书问题时可临时 WEBHOOK_VERIFY_TLS=false，不要当生产默认。

常用环境变量

变量含义
DOMAINS_FILE域名列表路径
STATE_FILE状态 JSON 路径
PLAYWRIGHT_HEADLESStrue = 容器 Chromium；false = 本机 Chrome
IGNORE_HTTPS_ERRORS浏览 Google 页时忽略证书错误
ALERT_WEBHOOK_URLTeams / Power Automate 触发器
WEBHOOK_VERIFY_TLSPOST Webhook 时校验 TLS；生产应为 true

RESULT_TIMEOUT_MS等待结论文案超时
MAX_RETRIES默认 3

2. Docker

无头 Chromium，状态挂到宿主机目录。

docker run --rm --ipc=host \
  -v "$PWD/docker-state:/data" \
  -e ALERT_WEBHOOK_URL=… \
  jevinwanglb/portal-monitor:sha-xxxxxxx

开发镜像用 sha-xxxxxxx，生产用 v1.x.x。不要把未验证的 SHA 直接指到 CronJob。

3. Kubernetes

Namespace：portal-monitor。 Secret portal-monitor-alert 的 key webhook-url 不要进 Git。

配置 ConfigMap + Secret

ConfigMap 挂到 /app/domains.txt；Secret 注入 ALERT_WEBHOOK_URL。改域名只 apply ConfigMap。

↓
测试 Job + 测试 PVC

portal-monitor-test 挂 portal-monitor-state-test，不改生产状态。

↓
生产 CronJob + 生产 PVC

portal-monitor 每 10 分钟跑一次，状态写在 portal-monitor-state 的 /data/status.json。

Test

镜像通常是 CI 的 sha-xxxxxxx。一次性 Job，跑完不占 CPU。状态在测试盘。

Production

镜像用 v1.x.x。Cron */10 * * * *，Forbid 禁止重叠。PVC 是 RWO。

  • gp3 多为 WaitForFirstConsumer：PVC 可能先 Pending，第一个用盘的 Pod 调度后才 Bound。
  • 删 Job / Pod，不要删 PVC，否则下次会当成首次检查，UNSAFE 可能再告一次。
  • 手工立刻跑生产：先 suspend: true，再 kubectl create job --from=cronjob/portal-monitor …。Forbid 不管手工 Job；和生产 Cron 同时跑会抢同一块 RWO。
  • cd-test-job.yml 挂测试 PVC；生产只走 cd-cronjob.yml。不要直接 apply 带 IMAGE_PLACEHOLDER 的 yaml。

4. CI / CD

日常测试跟 main 的 SHA；生产跟 Semver tag。不要把未验证的 sha-… 直接指到 CronJob。

1 · CI push main → 构建镜像

改了 app / Dockerfile / requirements 等会触发 docker-publish.yml，推送 jevinwanglb/portal-monitor:sha-<7位>。

↓
2 · 测试 CD 自动或手动跑 Test Job

CI 成功后 cd-test-job.yml 自动跑 SHA 镜像（也可手动填 tag）。 Runner arc-runner-set-portal apply 测试 PVC + ConfigMap，跑 portal-monitor-test 并打日志。

↓
3 · Release 确认无误后打 Git tag

打在已测过的 commit 上，例如 v1.0.1，产出 jevinwanglb/portal-monitor:v1.0.1。 这份 tag 镜像不会自动进 Test Job。

↓
4 · 生产 CD 手动更新 CronJob

先用同一 tag 手动跑 cd-test-job.yml，通过后再跑 cd-cronjob.yml 更新生产 CronJob。

  • 改域名：改 k8s/configmap.yaml 再 apply；解析逻辑变了必须发新镜像。
  • CD runner 需要能 kubectl 到 portal-monitor namespace。
  • 上生产前：Actions → CD - Test → image_tag=v1.x.x，过了再跑生产 CD。

怎么确认「没检测出来」是哪一种

先看 Job 日志：出现 Found N domain(s) 说明本轮 Pod 已读到 ConfigMap。

  • UNSAFE 且 No status change — 检测成功，只是不重复告警。
  • UNKNOWN + timed out waiting — 20s 内没出现已知文案，或文案变了；会写 debug 文件。
  • UNKNOWN 无超时 — Google 明确说无法给简单结论，或短语未匹配。

Pod 已 Completed 时不能 exec。起一个临时 busybox 挂同一 PVC（RWO：等 monitor 结束再挂）：

ls -l /data
cat /data/status.json
head -c 4000 /data/debug_<域名>.txt

debug 文本就是当时页面的 innerText。 若里面已有 Some pages on this site are unsafe，但日志仍是 UNKNOWN， 说明解析短语没跟上页面（这类问题已在 UNSAFE_PATTERNS 里补过）。

修解析必须发新镜像，只改 ConfigMap 不够。
